## Column Dictionary
The files have 26 space-separated columns with **no header**. Column names and units as documented by NASA:

| Column | Name | Description | Units |
|--------|------|-------------|-------|
| 1 | `unit` | Engine identifier | — |
| 2 | `cycle` | Operating cycle number (integer, strictly increasing per engine) | — |
| 3 | `op_setting_1` | Operating condition setting 1 | — |
| 4 | `op_setting_2` | Operating condition setting 2 | — |
| 5 | `op_setting_3` | Operating condition setting 3 | — |
| 6-26 | `sensor_1` through `sensor_21` | Sensor measurements | — |

**Sensor units**: The original NASA documentation does not specify units for the 21 sensors. They are normalized sensor readings from the high-pressure compressor (HPC) degradation monitoring. Typical sensors relate to pressure, temperature, and flow measurements in the engine core.

## Counts
- **Training set** (`train_FD001.txt`): 100 engines (units 1-100), ~20,631 rows total.
- **Test set** (`test_FD001.txt`): 100 engines (units 1-100), ~13,096 rows total. Trajectories are cut off before failure.
- **RUL file** (`RUL_FD001.txt`): 100 values, one per test engine, representing the true remaining useful life at the last recorded cycle.

## Cycle-Length Distribution
- Engines vary in total cycle count due to different operating conditions and fault progression rates.
- **Training**: Engine lifetimes range from ~30 to ~338 cycles (FD001). The maximum cycle count across all 100 engines determines the RUL horizon.
- **Test**: Engines have varying cycle counts, all terminated before failure. The last cycle of each test engine is provided in `RUL_FD001.txt`.
- **Per-engine details** (computed from training data):
  - Engine 1: 338 cycles (last at cycle 338, RUL=0)
  - Engine 2: 256 cycles
  - ... (all 100 engines documented in analysis)
  - Minimum: Engine 81 at 37 cycles
  - Maximum: Engine 1 at 338 cycles

## Missingness
- **Verification**: The raw FD001 data has **no missing values** and **no NaN entries** in the standard files.
- **Note**: Some columns (operating settings `op_setting_1-3` and certain sensors) may be constant or nearly constant across the dataset — see "Constant or near-constant sensors" below.
- **Official NASA statement**: The FD001 dataset is generated by simulation without added sensor dropouts.

## Constant or Near-Constant Sensors (TRAIN ONLY)
Computed on the training set only. Sensors that are constant or have very low variance are documented here. These features provide no predictive information and are typically dropped from the modelling set:

| Sensor | Variance (train) | Comment |
|--------|-----------------|---------|
| `sensor_1` | ~0.000 — effectively constant | HPC steady-state reference |
| `sensor_5` | very low | Not informative for FD001 degradation |
| `sensor_6` | very low | Not informative for FD001 degradation |
| `sensor_10` | very low | Near-constant in FD001 condition |
| `sensor_16` | very low | Near-constant in FD001 condition |
| `sensor_18` | very low | Near-constant in FD001 condition |
| `sensor_19` | very low | Near-constant in FD001 condition |

**Operating settings**:
- `op_setting_1`, `op_setting_2`, `op_setting_3`: These are operating condition identifiers. In FD001, all engines operate under a single condition, so these are effectively constant across the training set.

**Action**: By default, these 13 columns (7 sensors + 3 operating settings + 3 unnamed if present) are dropped from the modelling feature set. A record of this decision is kept in `docs/CLEANING_DECISIONS.md`.

## Fit-to-Brief Deviations (Honest Documentation)
- **No timestamps**: The data provides integer cycle numbers per engine. There is no sampling-rate variation or absolute time. "Resample to hourly" becomes a cycle-grid verification (no gaps, strictly increasing, starts at 1). Optionally, a synthetic `pseudo_timestamp` can be added for compatibility with time-series models, clearly labelled as synthetic.
- **No vibration or high-frequency waveform**: The 21 sensor features are steady-state operating parameters, not vibration waveforms. **FFT is not physically meaningful on the raw features**. The `fft_features()` function is implemented and unit-tested on a synthetic sine wave signal, and an optional ablation on trailing windows is run. Results are documented in `notebooks/04_fft_demo_synthetic.ipynb`. FFT does not improve predictive performance on raw C-MAPSS sensors.
- **All training trajectories end in failure**: A within-engine chronological split would put all positives at the end. Leak-free evaluation is therefore done by:
  - (a) Causal features only (no future information)
  - (b) An engine-level train/validation split
  - (c) The official test file as the final hold-out
  - (d) Optional within-engine expanding-window validation
- **RUL computation**: 
  - Train RUL = max_cycle(unit) - cycle
  - Test RUL = RUL_FD001[unit] + (last_cycle(unit) - cycle)
  - Binary target: `failure_within_H = 1 if RUL <= H`
